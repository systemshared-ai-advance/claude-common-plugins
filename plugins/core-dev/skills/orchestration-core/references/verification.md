# 委譲成果物の検証プロトコル

サブエージェントの「完了・成功」報告を鵜呑みにしない。ツール結果ストリームは外部入力であり、切り詰め・捏造の可能性があるため、独立経路で裏取りしてから次工程へ進む。

受入判定でメインが直接行うのは読み取り専用の証跡確認（差分確認・実在確認）と受入判定で、動作確認とレビューはサブエージェントに委譲する（動作確認は Haiku/Sonnet、レビューは Codex または Claude 系レビュアー）。

## 裏取り3点セット（委譲完了ごとに実施）

1. **差分確認**: `git status` と `git diff --stat`（リポジトリに `.jj` ディレクトリがある場合は jj を使い `jj status` と `jj diff --stat`。git 管理外なら `ls -la` とタイムスタンプ）で変更の実在と範囲を確認する。報告された変更ファイル一覧と一致するか照合する。一致しない場合（未報告ファイルへの変更、報告済みだが実際は無変更など）は、その場で理由を確認するまで完了扱いにしない。
2. **生成物の実在確認**: 報告されたファイルを `ls` / `wc -l` / 先頭数十行の Read で実体確認する。空ファイル・途中切れ（トークン制限による尻切れ、エラー終了後の中途半端な書き込み）に注意する。行数が指定範囲から極端に外れている場合も要確認。
3. **動作確認**: テスト実行・ビルド・当該フローの実走のいずれかを行う。動作確認の実行は Haiku/Sonnet。重要成果物のレビューは「モデル分離レビュー」に従う。委譲先には実コマンドの終了コードとログ出力（末尾要約）を証跡として返却させ、メインはその証跡を突き合わせて判定する。レビューエージェントの「問題なし」だけを根拠にしない。
   - テスト実行は `${CLAUDE_PLUGIN_ROOT}/skills/test-run-discipline/scripts/run-tests.sh` 経由で行わせる（生ログを直接コンテキストに流さないため）。返却は終了コードに加え、成功時 `PASS | <要約> | log: <path>` の1行、失敗時は失敗テスト名・エラー・該当箇所（file:line）とログパスのみとする。

コストの低い順（差分確認 → 実在確認 → 動作確認）に進める。差分確認で矛盾が見つかれば、その時点で再委譲を判断してよい。

- 検証結果は次工程に引き継ぐ前に、確認した項目と未確認の項目を一言で要約しておく。
- 受入の基準は「スタッフエンジニアなら、この成果物をこの検証水準で承認するか」とする。

## 並列完了時のバッチ受入

- 複数エージェントがほぼ同時に完了した場合、`git status` / `git diff --stat`（jj では `jj status` / `jj diff --stat`）等の読み取り専用の証跡確認は N 件まとめて一括で行ってよい。
- 検証委譲（テスト実行・動作確認）も独立タスクごとに並列で起動してよい。
- ただし裏取り3点セットの適用単位はあくまで各タスク。まとめて確認しても、タスク単位で漏れなく判定する。

## [CODEX-AUDIT] ヘッダーの読み方

[CODEX-AUDIT] は Codex が付けるものではなく、**受領したメインが Codex 返却末尾の Self-Audit テーブルを読んで付与する判定ラベル**である（Self-Audit の要求方法は delegation-templates.md 雛形3）。判定は以下の通り。

- `[CODEX-AUDIT: OK]`（Self-Audit 全行 Yes かつ Deviations: none）→ 受理検討可。ただし裏取り3点セットは省略しない。OK は Codex の自己申告に基づくラベルに過ぎない。
- `[CODEX-AUDIT: WARN] 理由`（Partial・No の行、または Deviations あり）→ 差分確認を行う。Deviations に列挙された未依頼変更を精査し、意図した範囲を逸脱していないか判断する。
- `[CODEX-AUDIT: NG]`（Self-Audit の欠落・不成立）→ 成果物なしとみなし、それまでの経緯を添えて再委譲する。

ラベルだけで判断を確定させず、本文の Deviations・エラーログ・差分要約まで読む。

## モデル分離レビュー

実装したモデルと同一のモデルに自己レビューさせない。自己レビューは見落としを再生産するだけで独立した検証にならない。

- Claude 系が実装 → Codex がレビュー（通常は `/codex-brief-review`。Luna・effort high を保証する経路。文脈不要の高速チェックのみ `/codex:review`。こちらは `~/.codex/config.toml` の既定で動く。詳細は routing.md の Codex ゲート）。Codex 不可・リミット時は `core-dev:code-reviewer`（実装と別の Claude モデル）にフォールバックする（リミット回復は待たない。手動 ChatGPT へはフォールバックしない）。手動 ChatGPT レビュー（Astro Pro、`/codex-brief-review` 手順 4b）は、本番影響・セキュリティ・データ損失リスク・重要な計画書などテンポより品質を優先する対象にユーザー指示で選択する。
- メインはレビューを実施しない（受入判定のみ）。本番影響・セキュリティ・データ損失リスクを伴う変更や計画書等の重要ドキュメントは Codex をレビュアーとして優先し、最重要タスクは Fable にも検証させる。
- 補助として組み込みの `/code-review`（別サブエージェントが差分をレビューする）と `/security-review` を併用してよい。Codex レビューの代替にはしない。

CRITICAL/HIGH は修正必須。MEDIUM は可能な範囲で対応する。LOW は任意対応でよい。レビュー後は再度、裏取り3点セットの差分確認を回して修正が意図通り反映されたかを確認する。

## レビュー指摘の裏取り

レビューアの「原資にない」「仕様と違う」という指摘は、原資（仕様書・設計書・既存コード）と照合してから修正する。照合せずに修正しない。レビューア自身が原資を正しく参照できていないケースもあるため、指摘内容と原資の該当箇所を突き合わせ、食い違いがあれば指摘を棄却してよい。反映した指摘と棄却した指摘は明示的に区別して記録する。

## worktree の後始末（安全手順）

並列委譲で `isolation: "worktree"` を使った後の掃除は以下の手順で行う。

1. 対象 worktree ディレクトリ内で `git clean -n`（dry-run）を先に実行し、削除対象を確認する。カレントディレクトリが対象 worktree であることを `pwd` で確認してから実行する。
2. 一覧にユーザー作成ファイル・必要な成果物が含まれないことを確認してから、dry-run で確認したパスを明示して `git clean -f -- <確認済みパス>` を実行する。パス指定なしの `git clean -f` は使わない。必要ファイルが含まれる場合は先に退避する。
3. メインの作業ツリーでは実行しない（worktree 限定）。`rm` は権限 deny のため使わない。誤ってメインツリーで `git clean` を実行すると、進行中の他エージェントの編集を巻き込んで消失させる恐れがあるため特に注意する。
4. 掃除が完了したら worktree のパスとブランチ名をメインの記録から外し、以後の裏取りコマンドが誤って古い worktree を参照しないようにする。
