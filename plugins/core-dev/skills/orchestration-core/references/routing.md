# モデルルーティング判定表

即決表は SKILL.md にある。本書はその補足で、モデル階層・effort の指定・判定基準・Codex ゲート・コストガード・エスカレーションを定める。

原則は「最も安い十分なモデル」。コストと性能の序列は Haiku < Luna < Sonnet < Opus < Fable。Luna は Codex 側のモデル（ChatGPT サブスク定額）で、リミットが小さいためレビュー専用にする（Step 3）。

- **Fable サブエージェントの用途**: 最重要タスクの検証とレビュー、重要な設計、規模の大きい計画立案に使う。調査と実装には使わない（単価が最も高いため）。計画に付随する調査は Opus / Sonnet に委譲する。

## effort の指定

`effort` を省略したサブエージェントの effort は、次の順で決まる: 環境変数 `CLAUDE_CODE_EFFORT_LEVEL` → エージェント定義またはスキルの effort → 環境変数 `CLAUDE_CODE_SUBAGENT_EFFORT` → セッションの設定（`/effort` または settings）。ユーザーが明示しない限り `effort` を渡さず、この順に従わせる。

- Workflow ツール: `agent(prompt, {model, effort})` の `opts.effort` は省略する。
- Agent ツール: `effort` パラメータは省略する（スキーマ上も「ユーザーや CLAUDE.md・スキルが明示的に求めた場合のみ設定し、自分の判断では設定しない」とされている）。
- ユーザーが effort レベルを明示的に指示した場合（例:「xhigh で」）のみ、そのレベルをそのまま渡す。
- 委譲プロンプト冒頭に思考の深さを英文で明記することは行わない。
- サブエージェント全体の effort の既定を変える場合は環境変数 `CLAUDE_CODE_SUBAGENT_EFFORT` を使う（model の既定は SKILL.md「1. モデルルーティング」の `model` の項）。

## Step 1: 即決表

SKILL.md「1. モデルルーティング」の表で決める。該当する行がない場合だけ Step 2 へ進む。

## チーム or サブエージェント

Agent Teams（`name` 付きで起動するチームメイト）は、各チームメイトが独立した Claude インスタンスで、トークン消費がサブエージェントより大幅に増える。既定はサブエージェント。

- 必須条件: 作業中にチームメイト同士が連絡し合う必要がある。連絡なしで分担できる作業は、サブエージェントの並列 fan-out にする。
- 例: 競合する仮説を持つ調査・レビュー・デバッグ、層をまたぐ作業。逐次作業、同一ファイルの編集、依存関係が強い作業、結果だけが要る作業は適さない。
- 規模: チームメイト3〜4名。
- チームメイトのモデル: 固定の既定は置かず、作業単位の性質で選ぶ。
  - Opus: 単位の主な仕事が判断である場合（設計判断、競合する仮説を立てるデバッグ・検証、他のチームメイトとの調整）。チームが適する場面の大半はこれに当たる。Opus コストガードを適用する（起動前にスコープを宣言する）。
  - Sonnet: 単位の範囲と完了条件が明確で、チームメイトは委譲と受入判定だけを行う場合。
  - 迷ったら、作業単位全体を「Step 2: 判定基準」で判定する。
  - `model` を明示する（省略時の決定順は SKILL.md「1. モデルルーティング」の `model` の項）。Codex はチームメイトにしない。

## Step 2: 判定基準

即決表で決まらないときは、次の観点で上位のモデルが要るかを判断する。重い観点が多いほど上位のモデルに寄せる。

- 影響するファイルの数と結合の強さ: 1ファイルで閉じるか、複数ファイルの整合を取る必要があるか。
- 設計判断の要否: 手順が決まった作業か、方式を選ぶ判断を含むか、横断的なアーキテクチャ判断を含むか。
- 誤った結果のコスト: 使い捨て・可逆か、本番・セキュリティ・データ損失に関わるか。
- 要件の曖昧さ: 完了条件が明確か、解釈を要するか。

どの観点も軽ければ Haiku、通常の実装判断の範囲なら Sonnet、設計判断や横断的な判断を含むなら Opus に割り当てる。本番・セキュリティ・データ損失に関わる作業は Sonnet 以上にする。規模の大きい計画は Fable も検討する。

## Step 3: Codex ゲート

Codex はレビュー専用。回してよいのは次のタスクだけ:

- コードレビュー・計画レビュー（Claude 系が実装・立案した成果物）
- レビュー観点のセカンドオピニオン
- 重要成果物のレビュー（本番影響・セキュリティ・データ損失リスクを伴う変更、計画書等の重要ドキュメント）

Codex の呼び出し経路とモデル・effort:

- `/codex-brief-review`（個人環境のスキル。本プラグインには含まれない）を導入している環境では、それが読み取り専用・モデル・effort を明示して `codex exec` を実行する経路になる。Luna・effort high を保証できるのはこの経路だけ。
- `/codex:review`、`/codex:adversarial-review`、`codex:codex-rescue` は、指定しない限りモデルも effort も渡さず、`~/.codex/config.toml` の既定（`model` / `review_model`、`model_reasoning_effort`）が適用される。`Luna` という名前は有効な `--model` 値ではないので渡さない。
- `codex:codex-rescue` は、レビュー専用の依頼でない限り既定で `--write` を付ける。レビュー依頼文には「読み取り専用のレビューで、ファイルを変更しない」ことと effort high を明記する。

最重要タスクの検証は Codex ではなく Fable に回す。実装・調査・計画立案・Web 調査、および定型・低難度の作業は Codex に回さない（Claude 系で足り、Codex のリミットを消費するため）。

依頼時の注意:

- ローカルファイル読取の可否は環境ごとに異なるため、初回に既知テキストを読ませるプローブで確認し、結果を記録する。返却は [CODEX-AUDIT] と裏取り3点セット（verification.md）で検証する。
- 確実性を優先する場合は、レビュー対象のコード・資料を委譲文にインライン貼付する。
- 依頼は小さな単位に分割する（失敗時の切り分けとリミット節約のため）。
- 認証は ChatGPT サブスク。`OPENAI_API_KEY` は設定しない（設定すると API 従量課金に切り替わる）。

## Opus コストガード

背景: 実測で Opus がコスト全体の約87%を占め、単発セッションで高額になった事例がある。

- Opus への委譲は1タスク単位に分割する。複数論点を1委譲に詰め込まない。
- 委譲文にスコープ（対象ファイル上限・停止条件・返却形式）を書く。

## Haiku に向く作業の例

Markdown や frontmatter の一括修正、リンク/パス実在チェック、ドキュメントの見出し構成の抽出、解答分布の集計、ビルド/テストログの収集と要約、ファイル一覧・行数カウント。

## エスカレーション

- 同一タスクで2回失敗したら1段上のモデルへ引き上げる（Haiku→Sonnet→Opus→Fable）。同一モデルで3回以上リトライしない。Codex はエスカレーション先に含めない。
- Fable サブエージェントでも2回失敗した場合は作業を止め、試したこと、判明している範囲の原因、必要な対応をユーザーに報告する。
- エスカレーション時は失敗の経緯（何を試して何がだめだったか）を委譲文に含める。
